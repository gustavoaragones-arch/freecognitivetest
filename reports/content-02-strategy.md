## 5. Remaining semantic template defects (Part 2)

### A. `body_attention.en[3]` — ADHD-specific sentence on non-ADHD pages

**Traced to:** `assets/data/content-variations.json` → `body_attention.en[3]` (and `es[3]`/`fr[3]`), selected by `pickParagraphs()` in `scripts/generate-programmatic-pages.mjs`, themed via `inferBodyTheme()`'s broad `/attention|focus|adhd|.../` slug regex.

**Mechanism:** any page whose slug matches the "attention" theme regex is eligible to draw from the full 6-sentence `body_attention` pool, including one sentence written specifically about ADHD.

### B. `body_memory.en[5]` — bilingual-specific advice on non-bilingual pages

**Traced to:** `assets/data/content-variations.json` → `body_memory.en[5]` (and `es[5]`/`fr[5]`), same selection mechanism, "memory" theme (the default theme for ~89% of the corpus).

**Chosen fix — smallest architecture that solves this class of bug, not just these two instances:** conditional (eligibility-gated) selection, not a pool rewrite and not new topic-specific pools. New file `scripts/lib/sentence-eligibility.mjs` declares, per pool key + index, an optional `pattern` a page's EN slug must match for that specific sentence to be eligible; entries with no rule remain eligible everywhere (fully backward compatible with the other 16 pool sentences, which are unrestricted). `pickParagraphs()`'s existing index-retry loop (already used to avoid picking the same sentence twice) was extended with one more skip condition: skip an index if it's already used **or** if it fails eligibility for this page, then continue to the next index using the same deterministic hash-derived starting point.

This means: pages that never would have drawn the restricted sentence are **completely unaffected** — same hash, same starting index, same result. Only pages that would have drawn a now-ineligible sentence get rolled forward to the next eligible one. No other pool was touched (`body_memory`'s other 5 entries, `body_dementia`'s 6 entries, `causes`/`benefits`/`tips`/`humanization` are all unmodified — confirmed by diff, see Part 11).

**Rejected alternatives and why:**
- *Rewrite the sentences generically* (like the CONTENT-01 "religious" fix) — rejected because these two sentences are legitimately good, specific content **for their actual topic** (ADHD, bilingualism); genericizing them would throw away real information CONTENT-01 already found to be scarce everywhere else in the corpus.
- *Split into topic-specific pools* — rejected as more architecture than the problem needs; two sentences don't justify a new pool-per-topic system, and it wouldn't generalize to the next mismatch found later.
- *Exclude the sentences from the theme pool entirely* — rejected because it would remove real, correct content from the only two pages it's actually written for (an ADHD page and a bilingual page).

**Pages affected — before vs. after** (computed deterministically by re-running the real selection logic with and without the eligibility gate; not sampled):

| | Rows changed |
|---|---|
| Total page-language rows whose selected paragraph set changes | **323** of 510 (63%) |
| — by cluster | `guides` 114, `exercises_intent` 111, `tests_audience` 63, `symptoms` 35 |
| — by language | EN 108, ES 108, FR 107 |
| — by theme | `memory` 297 (the bilingual fix, which was far more broadly over-applied than the ADHD one), `attention` 26 |
| Distinct EN slugs affected | 108 of 170 |

**Validation result:** confirmed 0 remaining eligibility violations when the fix is simulated corpus-wide (i.e. re-running selection with the gate active produces 0 pages where `body_attention[3]` lands on a non-ADHD page or `body_memory[5]` lands on a non-bilingual page).

**Decision — not applied to existing files this phase.** The CONTENT-02 brief explicitly says "DO NOT rewrite hundreds of pages" as a top-level constraint for this phase. 323 affected rows (108 distinct EN pages, more when ES/FR are counted individually) crosses that line, even though each individual change is a single-sentence substitution. **The source fix is live now** (any future regeneration is permanently correct), and the full before/after diff is computed and saved (`reports/content-02-gate-results.json` covers the gate; the diff itself is in this session's working data and can be reproduced by re-running the same simulation against the current `content-variations.json`). **Recommendation: applying this diff to the 108 already-published EN pages (+ ES/FR) should be the first concrete action of CONTENT-03**, using the same targeted, verified single-sentence patch method already proven in CONTENT-01 (37 files, zero collateral changes) — just at a larger, still-bounded scale, and ideally as its own explicitly-scoped task rather than folded into a broader phase.

## 6. Prioritization methodology (Part 4)

**GSC data: not available.** No Search Console export, analytics file, impressions/clicks data, or backlink data exists anywhere in this repository (confirmed by search) — the score below does not use or invent any of that. If GSC data becomes available, it should be added as a fifth weighted factor and this score re-run; until then, GSC performance is explicitly excluded rather than estimated.

Composite score (0–1) from four factors that **are** measurable locally, each independently justified:

| Factor | Weight | How measured |
|---|---|---|
| Distinct search intent | 30% | 1.0 if the page is not in a same-cluster keyword-overlap consolidation cluster (Part 5.); 0.3 if it is |
| Topic/entity strength | 30% | 1.0 if the slug names a specific clinical/practical entity (dementia, stroke, Parkinson's, ADHD, hearing, driving, medication, etc. — a fixed list drawn from terms that already anchor the site's core `cognitive-health`/`dementia`/`memory-tests` silos); 0.5 for a moderate entity (seniors, memory, cognitive decline generically); 0.2 for generic filler topics (e.g. "focus," "habits," "-edu") |
| Existing internal authority | 20% | log-scaled count of actual internal `<a href>` links pointing to the page, measured from the site's real link graph (not invented) |
| Cluster intent weight | 20% | `tests_audience` 1.0 (explicit tool-seeking intent) > `symptoms` 0.9 (high-urgency informational intent) > `exercises_intent` 0.8 > `guides` 0.7 (lowest-urgency informational) |

Buckets are quartiles of the resulting score distribution (min 0.321, p25 0.411, p50 0.560, p75 0.677, max 0.896) — not arbitrary cut points:

| Bucket | Range | Count |
|---|---|---|
| P1 | ≥0.677 | 43 |
| P2 | 0.560–0.677 | 46 |
| P3 | 0.411–0.560 | 40 |
| P4 | <0.411 | 41 |

## 9. B1 / B2 / B3 classification (Part 6)

Applied to the 91 "B" pages that are *not* in any Part 5 consolidation cluster (the C pages already have their own path). Sub-classified by the same P1–P4 priority score, since the score already encodes exactly the factors (distinct intent + entity strength + authority + cluster weight) that determine standalone viability:

| Sub-class | Definition | Count | 
|---|---|---|
| B1 — can become a genuinely useful standalone resource | P1/P2 priority | 71 |
| B2 — better merged into an existing resource | P3 priority | 20 |
| B3 — insufficient distinct intent, likely leave the index | P4 priority | 0 |

**B3 is empty by construction, and that's a real finding, not an error**: a page only ends up in "B" (rather than "C") because it already passed the distinct-intent test in Part 5. A P4-scoring page with generic framing and low authority almost always *also* shares a keyword with a sibling page — so it gets caught by the C/consolidation test first. If a future pass wants a populated B3 tier (standalone-intent pages that are nonetheless too weak to justify investment even alone), the scoring would need a fifth signal decoupled from consolidation-risk, e.g. topical breadth of the entity itself — flagged here rather than forced.

### Minimum editorial brief for B1 candidates

For every B1 page, before any rewrite happens, the brief must specify:

1. **Exact user intent** — one sentence, in the user's words, e.g. "A caregiver for a Parkinson's patient wants to know what memory changes are expected vs. concerning, and whether a home screening test is appropriate before a neurology visit."
2. **Required unique information** — ≥3 statements that are true of *this* topic and would read as wrong or irrelevant if the topic phrase were swapped for a sibling page's (the same test CONTENT-01 used to prove the current corpus has zero such statements).
3. **Required examples** — ≥1 concrete scenario specific to the audience/context named in the H1.
4. **Required practical guidance** — steps or considerations that a generic "brain health" page would not already cover.
5. **Required FAQ subjects** — ≥2 questions a user of *this specific* page would ask that a user of a sibling page would not.
6. **Appropriate internal tools/resources** — which of the site's actual interactive tests/exercises are genuinely relevant to this audience (not just the rotation-assigned `toolKey`).
7. **Evidence requirements** — per AUTH-01's existing sources policy (`sources-policy/`) and editorial standards (`editorial-standards/`) — not relaxed or bypassed for this remediation.
8. **What must NOT be generic boilerplate** — explicitly: none of `causes`/`benefits`/`tips`/`humanization`/the sitewide FAQ topup pool may be the *only* content on the page; they may supplement but not substitute for items 2–5.

This brief format is proposed, not yet applied to any specific page's content — no articles were written this phase.

## 10. Generator quality gate (Part 7)

**Implemented:** `scripts/lib/content-value-gate.mjs`, gate version `1.0.0`. Six checks, each independently explaining pass/fail:

| Criterion | Threshold | Source of threshold |
|---|---|---|
| `minUniqueStatements` | ≥3 | CONTENT-01 measured 0 in the current corpus |
| `minUniqueInformationalBlocks` | ≥2 | CONTENT-01 measured 0 |
| `minExamples` | ≥1 | CONTENT-01 measured 0 anywhere in the 510-page family |
| `minTopicFaqs` | ≥2 of 5 | CONTENT-01 measured 0 of 5 anywhere; FAQ pool has only 14 total questions across all 510 pages |
| `maxSharedContentRatio` | ≤60% | CONTENT-01: "B"-classified pages currently run at ≈100% |
| `distinctSearchIntent` | no shared topic keyword with an existing same-cluster page | Directly the check that identified all 79 current "C" pages |

Deliberately **not** hard-coded from the CONTENT-01 proposal without adjustment: the originally-proposed "≤15% max reuse of any single pooled sentence within a theme cluster" criterion was **dropped** from the implemented gate. Reason: that threshold is a property of the *existing shared pools* (which only have 6 items per theme, so *any* page drawn from them exceeds 15% reuse by construction — the pools themselves fail this test, not the pages), not something a single new seed row can control. Enforcing it per-page would produce false positives on every proposal regardless of quality. The correct fix for that concern is architectural (bigger pools or per-topic content, which `minUniqueStatements`/`minExamples`/`minTopicFaqs` already force) rather than a per-page gate criterion — so it was folded into `maxSharedContentRatio` instead of kept as a separate, unsatisfiable check.

**Verified against three test cases** (`scripts/lib/content-value-gate.mjs` exercised via a standalone test, not the live pipeline):
- A bare proposal shaped like the current architecture (no unique fields) → **fails all 6 criteria**, exactly as expected.
- A fully-briefed proposal (3 unique statements, 2 unique blocks, 1 example, 2 topic FAQs, ~43% shared-content ratio, no keyword collision) → **passes all 6**.
- A proposal that collides with an existing page's topic keyword → **fails `distinctSearchIntent`** (plus the content criteria, since it also had no unique fields).

**Output formats:** `scripts/validate-content02-gate.mjs` produces both `reports/content-02-gate-results.json` (machine-readable) and a human-readable stdout report; exits 1 if any new proposal fails.

## 11. Programmatic expansion freeze (Part 1)

**Frozen manifest:** `assets/data/programmatic-frozen-manifest.json` — snapshot of the 170 EN slugs that exist as of this phase, grouped by cluster. This is the grandfathering boundary: rows in the manifest are never evaluated by the gate and are never deleted, altered, or blocked by it.

**Guard wired into the generator:** `scripts/generate-programmatic-pages.mjs::main()` now runs the gate against every seed row **before** the destructive delete-and-regenerate step it already performs (it deletes prior output dirs from a manifest, then rewrites everything — this reordering means a failing new proposal now aborts before anything is touched, not after). Any seed row not in the frozen manifest is evaluated; if any fail, the script prints a deterministic failure report and exits with a nonzero code without writing or deleting anything. **The generator was not executed this phase** (running it would rewrite all 510+ output files' timestamps and sitemaps, which this phase's constraints prohibit) — its correctness is proven by the standalone gate tests above using the identical `evaluatePage()` function, and by `scripts/validate-content02-gate.mjs`, which today reports 0 new rows / trivial pass (since the manifest was just generated from the current seed file).

**Standalone CLI**, safe to run anytime without touching page output: `node scripts/validate-content02-gate.mjs`.

## 12. Noindex / remove decision framework (Part 8)

Not applied to any page. Conditions, explicitly not word-count-based:

| Action | Conditions (all must hold) |
|---|---|
| **RETAIN** | Page has ≥3 genuinely topic-specific statements not duplicated on any sibling page, AND is not in a Part 5 consolidation cluster, AND fulfills the search intent implied by its H1 without requiring the reader to already know the topic is "the same as" a sibling page's. A short page can qualify (e.g. a narrowly-scoped FAQ or tool page whose brevity matches genuinely brief user intent). |
| **IMPROVE** | Legitimate, distinct search intent (passes `distinctSearchIntent`) but currently fails one or more of `minUniqueStatements` / `minExamples` / `minTopicFaqs` / `maxSharedContentRatio`. This is every current "B1" page. Action: commission the Part 9 editorial brief; do not noindex while a brief is pending or in progress. |
| **CONSOLIDATE** | Page shares a topic keyword with ≥1 other same-cluster page AND pairwise content-overlap score ≥55/100 AND the topics are not independently distinct/high-stakes (see Part 5's "fog" and "cognition" clusters, which share keywords but were explicitly NOT recommended for consolidation because each cause is medically distinct). Word count is irrelevant to this test — a long page built from the same shared pools as its cluster-mates is still a consolidation candidate; a short page with a genuinely distinct entity is not. |
| **NOINDEX** | Consolidation target has been chosen and the canonical resource exists and contains everything the noindexed page covered, OR the page fails `distinctSearchIntent` with no realistic standalone future (generic filler topic, e.g. much of the "use"/"focus" clusters) AND scores P4 AND has ≤3 inbound internal links (i.e., the site itself doesn't treat it as important). Never applied purely because a page is short or purely because AdSense flagged the site broadly — always requires the specific per-page evidence above. |
| **REMOVE** (delete the page/URL, not just noindex) | Only after NOINDEX has been live long enough to confirm no meaningful residual traffic/links (requires GSC data this repo doesn't have — until then, prefer NOINDEX + redirect over REMOVE), AND the page contains no unique factual claim not already covered by its consolidation target, AND removal doesn't break an existing inbound link from a RETAIN-classified page (check the link graph first). |
